# 02 — `company.yaml`

> Implemented: `packages/kernel/src/config/company.ts`. Examples: `examples/company.full.yaml`, `examples/company.solo-dev.yaml`. Check any file with `holdco config check <file>`.
> 구현 완료: `packages/kernel/src/config/company.ts`. 예시: `examples/company.full.yaml`, `examples/company.solo-dev.yaml`. `holdco config check <file>`로 검사합니다.

## English

### Role

`company.yaml` is to a company what `tsconfig.json` is to a TypeScript project or `foundry.toml` to a Foundry project: one file, generated by `init`, owned by the Operator, read by every part of the kernel. It is locked (hook, managed settings, CODEOWNERS).

### Three rules for what goes in it

1. **Required-fixed things are absent.** There is no `verification: false`, no `sandbox: off`, no `inbox.default: approve`. A key that does not exist cannot be misconfigured.
2. **Required-adjustable things are present with floors.** The schema rejects values below `KERNEL_FLOORS` (audit sample ≥ 5, graduation samples ≥ 20, agreement ≥ 0.9, canary rate ≥ 1% when a COO exists). The fixed graduation conditions (last 10 labels agree, no rollback, no missed canary, not frozen) are not in the file at all; they live in `policy/graduation.ts`.
3. **Optional things are switches under `modules`.** Turning one off means removing its actions and its budget share too (`holdco remove department` does all three); until that is done, the schema rejects the leftovers, so a half-removed module can never run.

Secrets never appear. Fields that need one (`bot_token_env`, `webhook_env`, `heartbeat_url_env`) take the *name* of an environment variable; the schema rejects anything that does not look like one.

### Sections

| Section | Holds | Replaces |
|---|---|---|
| `company` | name, mission, time zone | — |
| `operator` | GitHub handle for CODEOWNERS | `@OPERATOR` placeholder |
| `alerts` | channels, heartbeat URL | "alert the Operator" with no channel |
| `runtime` | host, tick, concurrency, session timeout, lease grace, attempts | supervisor constants |
| `modules` | executive, departments, improvement, auto-graduation, juniors | "enable departments in strategy.md" |
| `engines` | which engines this company may use (`claude`, `codex`), the env var holding each key, and a price table for engines that report tokens but not cost | Claude-only assumptions |
| `roles` | engine, model and effort per role kind, with per-department overrides for seniors | model lines in agent files |
| `budget` | monthly cap, session cap, shares, provider-cap attestation | `${MONTHLY_*_BUDGET_USD}`, `per_department_share` |
| `projects` | id, repo path, class, share, locked globs, kill criteria, `merge: local \| github` and `merge_wait` (D51) | portfolio table in `strategy.md` |
| `policy` | windows, inbox, digest, release, audit, graduation, tripwires, delegation, executive | the remaining `${…}` placeholders |
| `envelopes` | pre-approved boundaries for T1 | envelope YAML in `policy.md` |
| `actions` | the action registry | registry YAML in `policy.md` |
| `executors` | per action, how the kernel performs it: argv with placeholders, env allowlist, undo, timeout (D50). Optional; actions without one are manual inbox items | "the Operator deploys by hand" |

`governance/strategy.md` keeps what only a human or the CEO reads: mission narrative, objectives, non-goals. Everything a machine acts on moves here.

### Composition rules (all enforced by `compositionErrors`)

| Rule | Error example |
|---|---|
| Department names are not reserved (`verification`, `executive`, …) | `'verification' is reserved` |
| A role exists for every enabled module (CEO, COO, Improvement, juniors) | `roles.coo is required` |
| Every role's engine is configured under `engines` | `engine 'codex' is not configured` |
| Every Codex model in use has a price | `no price for codex model` |
| `by_department` keys are enabled departments | `roles.by_department.legal` |
| COO (engine, model) ≠ CEO (engine, model) when the COO is on | `roles.coo must differ from roles.ceo` |
| Verification (engine, model) ≠ every producer: `senior`, `junior_worker`, each `by_department` override | `the judge may not share … roles.senior` |
| COO on ⇒ canary rate ≥ 1% | `canary_rate must be >= 0.01` |
| Session cap ≤ monthly cap | `session_max_usd cannot exceed` |
| Every enabled spender has a share > 0; no share for a disabled one; total ≤ 1 | `not an enabled spender` |
| Project ids unique; project shares ≤ 1; experiments need kill criteria | `experiments need kill_criteria` |
| Demotion threshold below graduation threshold | `demotion_agreement must be below` |
| Action owner is enabled | `department 'legal' is not enabled` |
| No evaluator ⇒ tier ≥ T2 | `cannot be below T2` |
| T1 ⇒ envelope or gate | `T1 needs an envelope or at least one gate` |
| Envelope references exist | `unknown envelope` |
| Reserved namespaces (`legal.`, `credentials.`, `governance.`, `operator.`, `prod.irreversible.`) ⇒ T3 + never | `reserved namespace` |
| Executors name registered actions, never merges or branches, and carry no shell syntax | `not a registered action`, `no executor allowed`, `drop shell syntax` |

All violations are reported at once, not just the first.

### Engines and roles

```yaml
engines:
  claude: { auth_env: ANTHROPIC_API_KEY }
  codex:
    auth_env: OPENAI_API_KEY
    prices:                       # Codex reports tokens, not dollars; the kernel meters from this
      gpt-6.1-sol: { input_per_mtok: 5, cached_input_per_mtok: 0.5, output_per_mtok: 40 }

roles:
  ceo:           { engine: claude, model: opus }
  coo:           { engine: codex,  model: gpt-6.1-sol, effort: high }   # second key, second provider
  senior:        { engine: claude, model: opus }
  verification:  { engine: codex,  model: gpt-6.1-sol, effort: high }   # judge on another provider
  improvement:   { engine: claude, model: opus }
  junior_worker: { engine: claude, model: sonnet }
  junior_reader: { engine: claude, model: haiku }
  by_department:
    gtm:         { engine: claude, model: sonnet }
```

### Model defaults

One table in the kernel (`packages/kernel/src/config/models.ts`) is the standard; the presets are generated from it (a test fails if they drift), `holdco roles preset <mode>` applies it, and the Operator overrides any cell with `holdco roles set` or by editing `company.yaml`.

| Slot | Plays | Claude Code | Codex |
|---|---|---|---|
| executive | CEO (and a COO on the same engine) | `opus` | `gpt-6.1-sol` / high |
| producer | department seniors, Improvement | `opus` | `gpt-6.1-sol` / high |
| judge | Verification — must differ from every producer | `fable` | `gpt-6-astra` / high |
| worker | `junior_worker` | `sonnet` | `gpt-6.1-sol` / medium |
| reader | `junior_reader` | `haiku` | `gpt-6.1-sol` / low |

Three modes assemble the `roles` block from those slots:

| Mode | Preset | CEO | COO | Seniors / Improvement | Judge | Juniors | Why |
|---|---|---|---|---|---|---|---|
| `claude` | `solo-dev` | opus | sonnet (if on) | opus | **fable** | sonnet / haiku | one provider; the judge is still a different model |
| `codex` | `solo-codex` | sol | astra (if on) | sol | **astra** | sol medium / low | same, on Codex |
| `dual` | `full` | Claude opus | **Codex sol** | Claude opus | **Codex sol** | Claude sonnet / haiku | the second key and the judge sit on another provider, so their errors are not the producers' errors |

Overrides: `holdco roles set senior claude:sonnet`, `holdco roles set senior@gtm claude:haiku`, `holdco roles set verification codex:gpt-6-astra:high`. Every change is validated: the judge may not share a producer's (engine, model), the COO may not share the CEO's, and a Codex model needs a price. Claude aliases are resolved by Claude Code; Codex ids and the example prices must be checked against your account.

A role kind says what a session may do (its capabilities come from its role file in `org/roles/`); the assignment says what runs it. Independence is compared on the pair (engine, model), so the same model name on two engines counts as different. Putting the judge or the COO on a second provider is not required, but it makes their errors less correlated with the producers', and `doctor` warns when CEO and COO share an engine. See `07-engines.md` for what each engine guarantees and what the kernel adds.

### Effective tier

The registry tier is a starting point. The tier the supervisor enforces is computed by `effectiveTier` (`packages/kernel/src/policy/tiers.ts`):

```
effective = registry tier
          + one step per active demotion          (automatic, immediate)
          then T2 → T3 if executive ≠ "ceo+coo"   (no second key)
```

For merges, `tierForChange` goes one step further: if the diff touches a locked path or an approval-required path (the CEO, COO and Verification definitions; in a project, its fixed and configured locked paths), the merge is T3 whatever its action id says.

Promotion is never automatic. When an action meets the graduation rule, the supervisor files an inbox item with the evidence; the Operator approves by editing `company.yaml` (or `holdco promote <action>`, which edits it on the Operator's behalf and commits). Demotions live in the state database and clear only when the action re-graduates.

### Change handling

The supervisor watches `company.yaml`. A changed file is validated first; if invalid, the supervisor keeps the previous config, alerts, and logs the errors. A valid change applies at the next tick. Changes that shrink a budget or disable a module also abort affected running sessions at their next tool call.

### Editor support

`bun run schemas` emits `packages/kernel/schema/company.schema.json`. With the comment `# yaml-language-server: $schema=…` at the top of the file, editors offer completion and check patterns. Cross-field rules are only enforced by `config check`.

## 한국어

### 역할

`company.yaml`은 회사에게 `tsconfig.json`이나 `foundry.toml` 같은 파일입니다. `init`이 생성하고, 운영자가 소유하고, 커널의 모든 부분이 읽습니다. 잠겨 있습니다(훅, managed settings, CODEOWNERS).

### 무엇을 넣는가: 세 규칙

1. **필수·고정은 파일에 없습니다.** `verification: false`, `sandbox: off`, `inbox.default: approve` 같은 키가 아예 없습니다. 존재하지 않는 키는 잘못 설정될 수도 없습니다.
2. **필수·강도 설정은 하한과 함께 있습니다.** `KERNEL_FLOORS` 아래 값은 스키마가 거부합니다(감사 샘플 5개 이상, 승격 샘플 20개 이상, 일치율 0.9 이상, COO가 있으면 카나리 1% 이상). 승격 고정 조건(최근 라벨 10개 일치, 롤백 없음, 카나리 놓침 없음, 동결 아님)은 파일에 아예 없고 `policy/graduation.ts`에 있습니다.
3. **옵션은 `modules` 아래 스위치입니다.** 끌 때는 그 모듈의 행동과 예산 몫도 함께 지워야 하고(`holdco remove department`가 셋을 한 번에 처리), 그 전까지는 스키마가 남은 항목을 거부합니다. 반쯤 지워진 모듈이 돌아가는 일은 없습니다.

시크릿은 절대 들어가지 않습니다. 시크릿이 필요한 필드는 환경변수의 **이름**을 받고, 이름처럼 생기지 않은 값은 거부합니다.

### 섹션

위 표와 같습니다. 핵심은 흩어져 있던 `${…}` 플레이스홀더, `policy.md`의 위임 범위·레지스트리 YAML, `strategy.md`의 포트폴리오 표가 전부 여기로 모인다는 점입니다. `strategy.md`에는 사람과 CEO만 읽는 것(미션 서술, 목표, 하지 않을 것)만 남고, 기계가 행동의 근거로 삼는 값은 전부 이 파일로 옵니다.

### 구성 규칙

위 표의 규칙을 `compositionErrors`가 모두 강제하며, 위반 사항을 첫 번째 하나가 아니라 한 번에 전부 보고합니다.

### 모델 기본값

커널의 표 하나(`packages/kernel/src/config/models.ts`)가 기준입니다. 프리셋은 거기서 생성되고(어긋나면 테스트 실패), `holdco roles preset <모드>`가 그 표를 적용하고, 운영자는 `holdco roles set`이나 `company.yaml` 편집으로 어느 칸이든 바꿉니다. 슬롯은 다섯 개: executive(CEO, 같은 엔진의 COO), producer(부서 시니어, 개선), judge(검증, 모든 생산자와 달라야 함), worker(주니어 작업자), reader(주니어 리더). Claude는 opus/opus/fable/sonnet/haiku, Codex는 gpt-6.1-sol(high)/gpt-6.1-sol(high)/gpt-6-astra(high)/gpt-6.1-sol(medium)/gpt-6.1-sol(low). 모드는 `claude`(solo-dev), `codex`(solo-codex), `dual`(full: 생산과 CEO는 Claude, COO와 심판은 Codex. 두 번째 열쇠와 심판이 다른 제공사에 있어 생산자와 같은 오류를 내지 않음). 변경은 `holdco roles set senior claude:sonnet`, `holdco roles set senior@gtm claude:haiku`처럼 하고, 모두 검증됩니다(심판은 생산자와, COO는 CEO와 (엔진, 모델)이 달라야 하고, Codex 모델은 가격 필요). Claude 별칭은 Claude Code가 해석하고, Codex 모델 ID와 예시 가격은 계정 기준으로 확인해야 합니다.

### 엔진과 역할

위 예시와 같습니다. `engines`에는 이 회사가 쓸 수 있는 엔진(`claude`, `codex`)과 키가 든 환경변수 이름, 그리고 비용 대신 토큰만 보고하는 엔진(Codex)의 가격표가 들어갑니다. `roles`에는 역할 종류마다 엔진·모델·추론 강도를 지정하고, 시니어는 부서별로 따로 지정할 수 있습니다. 역할 종류는 세션이 **무엇을 할 수 있는지**(권한은 `org/roles/`의 역할 파일), 배정은 **무엇이 그 세션을 돌리는지**를 뜻합니다. 독립성은 (엔진, 모델) 쌍으로 비교하므로 같은 모델 이름이라도 엔진이 다르면 다른 것으로 봅니다. 심판이나 COO를 다른 제공사에 두는 건 필수가 아니지만, 생산자와 오류가 덜 겹치게 해주고, CEO와 COO가 같은 엔진이면 `doctor`가 경고합니다. 엔진별 보장과 커널이 메우는 부분은 `07-engines.md`에 있습니다.

### 실효 등급

레지스트리 등급은 시작점입니다. 슈퍼바이저가 실제로 집행하는 등급은 `effectiveTier`가 계산합니다. 레지스트리 등급에서 활성 강등 하나마다 한 단계 올리고(자동, 즉시), 그 결과가 T2인데 경영진이 `ceo+coo`가 아니면 T3로 올립니다(두 번째 열쇠 없음).

머지에는 `tierForChange`가 한 단계 더 적용됩니다. diff가 잠긴 경로나 승인 필요 경로(CEO·COO·검증 정의, 프로젝트에서는 고정·설정된 잠금 경로)를 건드리면 행동 ID와 무관하게 T3입니다.

승격은 절대 자동이 아닙니다. 행동이 승격 기준을 충족하면 슈퍼바이저가 근거와 함께 인박스 항목을 올리고, 운영자가 `company.yaml`을 고쳐 승인합니다(`holdco promote <action>`은 운영자를 대신해 파일을 고치고 커밋). 강등은 상태 DB에 있고, 그 행동이 다시 승격될 때만 해제됩니다.

### 변경 처리

슈퍼바이저는 `company.yaml`을 감시합니다. 바뀐 파일은 먼저 검증하고, 잘못됐으면 이전 설정을 유지한 채 경보를 보내고 오류를 기록합니다. 유효한 변경은 다음 틱에 적용됩니다. 예산을 줄이거나 모듈을 끄는 변경은 영향받는 실행 중 세션을 다음 툴 호출 시점에 중단시킵니다.

### 에디터 지원

`bun run schemas`가 `packages/kernel/schema/company.schema.json`을 생성합니다. 파일 맨 위에 `# yaml-language-server: $schema=…` 주석을 두면 에디터가 자동완성과 패턴 검사를 해줍니다. 필드 간 규칙은 `config check`만 강제합니다.
